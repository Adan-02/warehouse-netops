# 独立接管练习

目标是你能解释、诊断和修改现有项目。练习围绕同一套仓库业务展开：你先预测、亲手操作、解释结果，助教根据卡点逐步提示。

从 [第一轮：一条消息的路径](01-message-map.md) 开始。每轮结束，参照 [记录模板](RECORD.template.md)，把自己的解释和实际观察写到仓库根目录的 `.local/learning/RECORD.md`。个人答案和自评留在本机。需要查运行位置和代码入口时，使用 [接手说明](../HANDOFF.md)；业务依据见 [项目设计](../../PROJECT.md)。

## 路线

安排 8–10 轮，每轮约 60–90 分钟。下表给出顺序；能独立完成的内容可以合并或跳过，遇到卡点则拆小任务。

| 轮次 | 亲手完成的任务 | 留下的成果 |
| --- | --- | --- |
| 1–2：建立项目地图 | 画出一条温湿度消息的设备、地址、端口、进程和数据流；解释权限为何这样划分；先预测三类中断的影响 | 一页自己的主链路图、预测及修正理由 |
| 3–5：追踪与诊断 | 追踪同一次采样；练习发布器、Broker、实验 WAN 的已知故障，再处理一次未告知原因的故障 | 检查顺序、排除其他可能的证据、恢复和复测记录 |
| 6–7：自主变更 | 在练习分支和临时环境中，把采样过期阈值从 20 秒改为 30 秒，查找入口、预测影响、检查差异、验证并回退 | 一次可解释的变更，以及源码、运行版本和数据状态的核对 |
| 8–10：Wokwi 综合练习 | 自己运行 ESP32＋DHT22，接入临时本地 MQTT 与看板，关联输入、采样、接收和入库 | 温湿度变化、停止采样、恢复连接、重启会话的关联证据 |

每轮只聚焦一个问题。先记录“预期会发生什么”，再选择能够区分假设的检查，最后解释实际结果与预期的差别。

## 提示怎样逐步增加

1. 你先说出目前的判断、依据和下一项检查。
2. 助教先指出观察位置，再提示相关概念，仍卡住时提供局部命令。
3. 卡住约 20 分钟后进入提示，避免反复执行同一检查。
4. 遇到配置风险或恢复失败，由助教介入恢复，并在记录中写明介入的位置。

普通练习只验证当前假设和直接受影响的行为。完整回归、自动全套验收与冷启动留给确实涉及这些范围的变更，以及最后复核。故障诊断先由你判断，自动脚本的最终结论放在后面核对。

## Wokwi 的位置

Wokwi 练习使用用户自己的有效 VS Code 许可证，许可内容和账号凭据留在本机。实际本地启动、网关联通、MQTT 和看板联调，分别按运行观察记录。

后期联调按一次有结束条件的实验组织：复用同一服务代码和镜像，使用独立端口、凭据、数据卷及明确的数据来源。完成后停止临时实例，保留可重复启动的入口。[现有固件说明](../../firmware/WOKWI.md) 可用于查阅配置，启动前要核对它所指的目标环境。

本地 Wokwi 联调证明固件到 MQTT、入库和显示的契约；现有四 VM 实验继续承担 OpenWrt 分区与远程运维的结论。两种证据分别记录。固件采用 QoS 0，串口 `Published` 之后还需核对实际接收与同一 `boot_id/seq` 的入库数据。

许可证或网关集中排查超过一小时仍无法运行时，暂停这个子任务，继续主线；不为它另建转发协议、长期观测系统或扩大现有网络权限。

## 怎样记录掌握

只有你实际完成操作并能解释结果，才在学习记录中标为掌握。看过讲解、复制过命令或自动验收通过，可以记录为已观察或借助提示完成。

最终看四项表现：

- 能画出主链路，解释各条访问权限对应的业务需要。
- 能处理一次未提前告知原因的故障，用证据排除其他可能并验证恢复。
- 能独立完成一次修改、验证和回退，分清源码、运行版本与数据。
- 能说明 Wokwi 证明的范围，以及换成真实设备后还需检查的部分。

每轮复盘用自己的话写几句：原先怎么想、观察到了什么、为什么修正、下次会先查哪里。助教只修正事实和推理，保留你的原始判断。
